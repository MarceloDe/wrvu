## N02c-rollback-harness — 15 problems

A self-test that returns 1 yields a pipeline exit of 0. This is the node's own designated INV-CHECKS-ACTUALLY-RUN witness and it is the one command in the block that is structurally incapable of reporting failure. Must be `set -o pipefail`, `${PIPESTATUS[0]}`, or a redirect plus `test $? -eq 0`.
- DONE_WHEN #4 CONTRADICTS ITS OWN VERIFY COMMAND. Line 263 writes `2> goals/evidence/N02c-rollback-harness/migrate-refusal.txt`; line 319 requires `git status --porcelain` to be byte-identical before and after. Verified: `.gitignore` does not cover `goals/evidence/` (`git check-ignore` exits 1), so the redirect creates an untracked file and the porcelain output necessarily differs. As written the check fails on a correct implementation. Redirect to a path outside the worktree, or scope the assertion to tracked paths and to `wc -c` on the audit log only.
- TWO DELIVERABLES ARE PROSE, NOT CONTRACTS. `scripts/verify/round-trip.mjs` and `scripts/verify/rollback-drift.mjs` appear nowhere in the `contracts:` block (lines 118-242). Their entire specification lives in YAML comments inside `verify.runtime` (lines 248-258, 273-278). Two of six runtime commands therefore invoke artifacts the Builder is never contractually required to produce, with behavior described narratively rather than as an interface. Promote both to `contracts:` with explicit signatures, arguments, exit codes and written artifacts.
- VERIFY DEPENDS ON AN UNCONTRACTED CLI SURFACE. Lines 263 and 317 both invoke `node scripts/db/migrate.mjs --target '<url>'`. Contract #5 (lines 210-223) extends migrate.mjs only with `isProductionTarget` and `hasSnapshotForHead` exports; nothing in this node or in the amendment establishes that N02a's migrate.mjs accepts `--target`. If it does not, the command exits on an unknown flag and `test $? -eq 3` fails for a reason unrelated to the rail. Contract the flag explicitly (`migrate.mjs accepts --target <connection-string>, defaulting to DATABASE_URL_UNPOOLED`), and state that this node adds it if N02a did not.
- CONTEXT_QUERY OMITS THE TWO FILES THE BUILDER MUST TOUCH (lines 58-62). A Builder loading only this query cannot satisfy contract #5 or the D38 reuse obligation. ## N03c-neon-branch-runner — 20 problems

- BLOCKING — fork-sim contract contradicts its own done_when. The contract for scripts/verify/db-jobs-attested.mjs says it 'exits 0 only when migrations succeeded, or when the PR genuinely came from a fork'. done_when #8 and the verify.runtime comment both demand that in the fork-sim run db-jobs-attested has conclusion 'failure'. Under the contract a simulated fork must produce exit 0 / success. A Validator cannot tell which outcome is a pass. Additionally the mode is described as 'a run with the fork guard forced true' — the guard expression head.repo.full_name == github.repository is TRUE for a non-fork, so 'forced true' would make the DB jobs RUN, not skip. The mode's name, its description and its expected result are three different things.
- BLOCKING — assertParentIsEmpty / ParentHasRowsError has no real-infrastructure verification anywhere, violating D20. The only verification of the row probe is 'node --test scripts/test/neon-guard.test.mjs', whose own comment excuses mocks on the grounds that these are 'pure predicates over Neon API JSON'. That is true of assertParentIsSynthetic and false of assertParentIsEmpty, which takes a connectionString and issues SQL. No selftest mode points at a parent that actually has rows, so PARENT_HAS_ROWS is never demonstrated against a real database — while notes.ROW-PROBE-COST identifies the reltuples optimisation as 'the single most likely way to silently disarm this node'. A Builder could ship assertParentIsEmpty as `return {tables:[],rows:0}` and every listed check would still pass. Required: a fifth mode (e.g. mode=parent-has-rows) that creates a scratch branch, inserts one synthetic row, points parent at it, and asserts NEON_GUARD_REFUSED: PARENT_HAS_ROWS in the log plus a zero-branch-delta afterwards.
- BLOCKING — the reaper deletes its own synthetic parent. neon-reaper.yml is contracted to 'delete every branch whose name starts with ci- and whose created_at is older than 24h'. The contracted synthetic parent is named `ci-template` (blocked_external item id: ci-template). It starts with `ci-` and will be older than 24h within a day of creation. The first scheduled reaper run destroys the one branch this node depends on, after which either CI fails or an operator re-creates a parent — the exact pressure toward `main` the node exists to remove. The reaper's selector must exclude the template explicitly (e.g. name matches ^ci-[0-9]+-[0-9]+$, keyed to the ci-<run_id>-<attempt> format the node already contracts) and the linter must assert that the template name cannot match the reaper's pattern.
- BLOCKING — it is undecidable which workflow the four run ids come from, so half the done_when cannot be evaluated. `migrations` and `db-jobs-attested` are contracted as jobs in .github/workflows/ci.yml, but all four run ids are produced by `gh workflow run neon-selftest.yml`, and then done_when #7, #8 and the final verify.runtime step read `.jobs[] | select(.name=="migrations")` and db-jobs-attested out of those selftest runs. Nothing in the contracts requires neon-selftest.yml to contain a job named `migrations` or `db-jobs-attested`, nor to call ci.yml as a reusable workflow. Either state that neon-selftest.yml invokes ci.yml via `uses: ./.github/workflows/ci.yml` (and contract that), or source those done_when from a real pull_request run of ci.yml and name that run id separately.
- BLOCKING — workflow_dispatch cannot exercise a pull_request-context expression, and the byte-identical static assertion makes this unresolvable as written. github.event.pull_request.head.repo.full_name is null on a workflow_dispatch event, so the contracted guard expression evaluates false on every selftest run. If neon-selftest.yml carries the expression byte-identically (as the ci-branch-cleanup.mjs assertion requires), its DB jobs skip in ALL four modes and the success / fail-midjob / bad-parent runs cannot create a branch at all. If the selftest instead overrides the guard from an input, the expression is no longer byte-identical and the static assertion fails. Pick one: factor the guard into a single reusable expression/composite whose ci.yml instantiation is asserted identical, and have fork-sim vary only the *input* to that expression, not the expression.
- BLOCKING — run-id-to-mode attribution is not independently re-derivable. `gh workflow run` prints no run id; all four modes dispatch the same workflow file; workflow_dispatch inputs are not returned by `gh run list`/`gh run view --json`. A Validator handed four ids has no way to confirm which id was mode=bad-parent without trusting the Builder's labelling, which done_when #1 explicitly forbids ('a Builder-supplied transcript is not accepted'). Fix with the mechanism the house already uses: contract `run-name: neon-selftest ${{ inputs.mode }}` in neon-selftest.yml, add `run-ids.md` to evidence (N02b's precedent), and make done_when #1 read the mode off `gh run list --json databaseId,displayTitle`.
- BLOCKING — done_when #2 rests on log output no contract requires. It demands 'a created branch id matching br-[a-z0-9-]+ and, later in the SAME job, a teardown line naming that same id'. The only log markers the contracts mandate are `NEON_GUARD_REFUSED: <code>` and `NEON_TEARDOWN: nothing-to-delete`. Nothing requires branch.mjs to print the created branch id, or deleteBranch to print the id it deleted, in any stable greppable form. Add contracts for `NEON_BRANCH_CREATED: <branch-id>` and `NEON_BRANCH_DELETED: <branch-id>`, and give done_when #2 the actual command that extracts and string-compares them.
