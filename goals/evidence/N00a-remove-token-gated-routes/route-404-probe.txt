## What these baseline numbers actually show

The two 404s are NOT evidence of removal. In the deployed build, `gate(req)` in
app/api/setup-clerk/route.js:32-36 and the token check in app/api/setup/route.js:105
answer an un-tokenised request with a hand-written `Response.json({error:"not found"},
{status: 404})`. A 404 without the token is exactly what the still-live, still-exposed
route returns. It is indistinguishable from a deleted route on this probe alone.

`/api/ocr-test` returning **405** is the useful line: that route exports only POST, so
Next answers GET with Method Not Allowed. 405 proves the route handler is STILL PRESENT
in the production build at probe time. After the deploy of this change it must become
404. That single status transition (405 -> 404) is the only unambiguous signal available
without the token header.

## Re-run after deploy (this is the run that proves done_when #1)

    curl -sS -o /dev/null -w '%{http_code}' https://fella.cc/api/setup-clerk        # 404
    curl -sS -o /dev/null -w '%{http_code}' https://fella.cc/api/setup              # 404
    curl -sS -o /dev/null -w '%{http_code}' https://fella.cc/api/ocr-test           # 404  (405 today)
    curl -sS -X POST -o /dev/null -w '%{http_code}' https://fella.cc/api/ocr-test   # 404  (was 404-from-gate)
    curl -sS -H "x-setup-token: $SETUP_TOKEN" -o /dev/null -w '%{http_code}' \
         'https://fella.cc/api/setup-clerk?inspect=1'                               # 404, and body must NOT be JSON allowlist
    curl -sS -H "x-setup-token: $SETUP_TOKEN" -o /dev/null -w '%{http_code}' \
         'https://fella.cc/api/setup?inspect=1'                                     # 404

The with-token probes must be run with the OLD token value, BEFORE N00b rotates it.
Once N00b rotates, the with-token probe can no longer distinguish anything.
